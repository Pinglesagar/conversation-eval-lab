Lesson 00 · The idea

What this project actually is

In one sentence It is a driving test centre for AI conversations: it puts an AI through a set route, records everything it did, and marks it against a scheme you can argue with.

Everything in this tour hangs off that one comparison, so it is worth setting out properly before any code appears.

The everyday version

A learner driver takes a test. An examiner sits beside them with a clipboard. A dashcam records the whole drive.

Afterwards there is a mark sheet. If the learner disputes a mark, you do not ask the examiner what they remember. You play back the recording.

And before you let that examiner mark anyone, somebody checks the examiner: give them drives whose right answer is already known, and see how many they get right.

This project

The learner driver is the . The set route is a . The dashcam is the .

The examiner is a mixture of (mechanical checks) and (an AI marking another AI).

Checking the examiner is , and here it is enforced: a judge that fails it cannot be used at all.

Click any word in and you get its definition, in plain language first. Every one of them is also listed in at the end.

Why build a test centre and not just test the AI

Ordinary software gives the same answer every time, so you can write assert answer == 4 and be done. An AI gives a slightly different answer every time, in a different order, in different words. That breaks the usual approach in three ways at once:

  • You cannot compare strings. "Your capital is at risk" and "you could get back less than you put in" mean the same thing and share no words.
  • One run proves nothing. It might have passed by luck. See .
  • The grader is software too, so the grader can be wrong. This turns out to be where most of the interesting bugs are.
The finding this whole repository opens with A grader marked a sales call 0 out of 4 for not asking questions. The adviser had asked five. The grader decided "is this a question?" by checking whether the sentence ended in a question mark — and the transcript it was handed had no punctuation at all. The agent was fine. The measuring instrument was broken.

The two things it is pointed at

The two systems under test that ship with it
roleplay/A coaching product for financial advisers: an AI plays a customer, a trainee practises a sales call, and software grades the result. Carries three deliberate, documented defects.
tablemate/A restaurant booking assistant with several agents handing work to each other. Also deliberately imperfect.

Both are broken on purpose. A test harness demonstrated against perfect software proves nothing: green results are equally consistent with a good agent and a blind test suite. The defects are real code paths, documented in exactly one place each, and nothing in the harness knows they exist.

What to take from lesson 00
  • The project is a test rig, not a product. The rig is lab/; the things being tested are roleplay/ and tablemate/.
  • Recording first, judging second. That order is the whole design.
  • The grader is software, so the grader is also under test.

Lesson 01 · The idea

The four stages, start to finish

In one sentence A conversation is described, then it happens, then what happened is written down, and only then is it graded.

Four stages, always in that order. If you remember nothing else about how the code is arranged, remember that the third stage exists — because almost every design decision in the repository follows from separating "what happened" from "what we think of it".

Walking one conversation through all four

  1. Described. Somebody writes a file: this customer, this situation, these are the things the agent must do. It is , so a compliance officer can read and edit it without touching Python.
  2. It happens. The harness runs the conversation. The agent under test is reached through an . The customer is played by a — sometimes scripted, sometimes a real language model, sometimes speaking out loud through a real speech engine.
  3. Written down. Every turn, every tool call, every audio chunk becomes an appended to the .
  4. Graded. ask mechanical questions. ask questions of taste. A turns the answers into a verdict.
The rule that falls out of this Nothing in stage 4 is allowed to ask the agent anything. It cannot call it back, cannot inspect its memory, cannot read its logs. If a fact is not in the trace, it does not exist for grading purposes. That sounds restrictive; it is what makes every number reproducible.
What to take from lesson 01
  • Describe, run, record, grade — in that order, always.
  • The recording sits between running and grading, and everything downstream reads only it.
  • That separation is what makes replay, dispute resolution and voice-versus-text comparison possible at all.

Lesson 02 · The idea

The trace: the one big idea

In one sentence A trace is the complete, ordered recording of one conversation — and it is the only thing any grader is allowed to look at.
The everyday version

Think of a hospital patient's notes. Every observation, every drug given, every doctor who saw them, each with a time, in order, in one file.

Nobody argues about care from memory. They open the notes. The notes are the record; opinions come afterwards and must point at a line in them.

Crucially, the notes are written as things happen, not reconstructed later by whoever is defending their decision.

This project

A trace is a file: one line per , in the order they happened.

Every verdict, every latency figure and every judge call is a function of that file. session_view(trace) is a pure function — same trace in, same view out.

It is written by the harness while the conversation runs, using an , not by the agent afterwards.

What one event really looks like

Straight out of a committed recording, shortened for width:

{"ts": 0.512, "kind": "tool_call", "actor": "agent",
 "payload": {"name": "record_disclosure",
             "args": {"code": "capital_at_risk", "turn": 3, "language": "en"}}}

Four fields, every time. , when, what of thing, and the . That regularity is why one checking engine can serve a voice call, a typed chat and a document-retrieval run without knowing which it is looking at.

The three things this buys you

  • A voice call and a typed call grade identically. Both become the same shape of file. When the two disagree, the difference is a real finding rather than a difference in test code.
  • Order without clocks. Checks decide on position in the list, not on timestamps. "Did the disclosure come before the recommendation?" is answered by index, so a slow machine cannot change a verdict.
  • Arguments end. A grade six months old can be recomputed from the file on disk, with no API key and no running agent.

What to take from lesson 02
  • A trace is an ordered list of events in one plain-text file.
  • Every grader reads it and nothing else.
  • Order is decided by position in the list, never by wall-clock time.

Lesson 03 · The idea

Events: the seventeen kinds

In one sentence The recorder can write seventeen sorts of line, and knowing what each one means is most of knowing how the system thinks.

These are the entire vocabulary. Everything the harness understands about any conversation is expressed in these terms.

The conversation itself
session_startA conversation began. Carries the settings it began with.
caller_utteranceThe person (or the simulated person) said something.
agent_utteranceThe agent said something.
session_endIt finished, and why it finished.
Things the agent did, not just said
tool_callThe agent used a tool: looked up a booking, recorded a disclosure, raised a compliance flag. The arguments are recorded.
tool_resultWhat came back, and whether it worked.
agent_handoffOne agent passed the conversation to another — a greeter handing over to a booking specialist.

That distinction between said and did is the important one. An agent that says "I've booked that for you" without a matching tool_call has lied, and the pair of events is what makes catching it mechanical rather than a matter of opinion.

Voice
audio_emittedAudio was produced, with its checksum and which engine made it.
audio_deliveredAudio arrived at the other end.
agent_audio_first_byteThe very first moment of the agent's reply — the number a caller experiences as "how long before it started talking".
agent_audio_completeIt finished speaking.
transcript_in / transcript_outSpeech turned into text, and text about to be turned into speech. Both transcripts are kept: the tidy one and the raw one.
transport_connected / disconnectedA real call connected or dropped.
Reserved, and honest about it
interruption_startedSomebody talked over somebody else.
interruption_acknowledgedThe agent noticed and stopped.
A small lesson in how this repository writes things down Those last two kinds exist, and the code that writes and reads them exists — but no adapter has ever discovered a real interruption; the events are currently written from constructed timings. Rather than let that pass as a feature, the schema marks them reserved and the limitations page says so. When you read the repository, that pattern repeats: the honest status is written next to the capability.

One design decision worth noticing: , not a closed list the code refuses to look past. A future adapter can emit a kind this version has never heard of, and the file still loads. Tooling reports unknown kinds instead of crashing on them.

What to take from lesson 03
  • Seventeen kinds cover conversation, tools, handoffs and voice.
  • Said and did are separate events, which is how a false claim becomes mechanically detectable.
  • Unfinished capabilities are labelled reserved rather than quietly shipped.

Lesson 04 · Setting up a test

A scenario, line by line

In one sentence A scenario is one test case written as a readable text file: who the customer is, what happens, and what must be true afterwards.
The everyday version

A restaurant's mystery-shopper brief. It says which branch, what to order, what to complain about, and what the shopper must confirm: were you greeted within a minute, were allergens mentioned, was the bill itemised.

The brief is written by the person who knows the standards — not by the person who writes the software.

This project

A is a YAML file. YAML is a plain-text format designed to be edited by people: names, colons, indentation, no brackets.

195 of them live under scenarios/. A compliance officer can add one without opening a Python file.

A real one, taken apart

This is scenarios/roleplay/pitch/pitch-ask-before-the-cost-disclosure.yaml, abbreviated but not altered:

id: pitch-ask-before-the-cost-disclosure
title: The signature requested before the charge was mentioned
customer: cautious_saver
tags: [closing, disclosure, known-gap, objection-handling]

trainee:
  role: retail investment adviser
  turns:
    - Before I show you anything, what would you want this money to be doing for you in ten years?
    - The fund I have in mind is a balanced growth fund. Your capital at risk is real...
    - Shall we get the paperwork started while you are here?

expectation:
  human_verdict: pass
  reason: >-
    All three disclosures are eventually given and both objections are answered...
    What the arithmetic cannot see is that the customer was asked to sign before
    she had been told what the product costs.

tools:
  expected: [record_disclosure, resolve_objection, score_session]
  min_calls: {record_disclosure: 3, resolve_objection: 2}
  args:
    - {tool: score_session, arg: total, op: eq, value: 18}
Every block, and what it is for
idThe permanent name. Reports, selection and fixtures all refer to it, so it never changes once written.
titleA sentence a human reads in a report. Notice it describes the situation, not the assertion.
customerWhich the AI plays. Defined in its own file, reused across scenarios.
tagsA closed vocabulary. A typo here is a loud load error, not a silently empty run.
trainee.turnsWhat the agent under test says. In scripted mode these are used verbatim; in live mode a real model improvises instead.
expectationWhat a human thinks the verdict should be, and why. This is the hand label the graders get measured against.
toolsThe mechanical assertions: which tools must be called, how many times, with what arguments.

The part people miss

expectation.human_verdict is not the test's answer. It is the human's answer, recorded separately, so the harness can ask a different question: how often does our grader agree with a person?

That single field is what turns a test suite into a measuring instrument. Without it you can only ask "did the agent pass?" With it you can ask "is our idea of passing any good?" — and that is how this repository found that one grader agreed with the human reviewer on who should pass but caught only 9 of the 32 sessions that should have failed.

Where scenarios live

scenarios/advisory/ (31)Regulated compliance rows, including the four cited registers.
scenarios/audio/ (21)Voice rows: noise, packet loss, codecs, accents.
scenarios/edge/ (20), happy/ (15), adversarial/ (12)The restaurant domain: ordinary cases, awkward cases, hostile cases.
scenarios/personas/ (9), voice/ (8)Reusable characters and voice settings that rows point at.

Writing them in Excel instead

YAML is readable, but it is still a programmer's file: one wrong indent and it will not load. The people who actually know what a suitability report must contain have a spreadsheet open all day. So the corpus converts both ways.

The loop
make scenarios-excelWrites every committed scenario into one workbook: a Scenarios sheet, a Turns sheet, an Assertions sheet, and a Reference sheet listing every legal value.
—The domain expert edits it. Sort, filter, copy a row to make a variant, hand it round for sign-off.
… check <file>Validates the workbook and writes nothing.
… import <file> --to-yamlWrites the YAML back. Only scenarios whose meaning changed are rewritten, so the diff a reviewer reads is exactly what the expert edited.

The rule that keeps it safe: an Excel row gets no validation of its own. It is converted into exactly the same dictionary the YAML parser produces, then handed to the same model. One rulebook, in one place. A test exports all 70 scenarios, reads them back, and compares every field — so a field the converter forgot to carry fails loudly rather than going missing.

Why YAML is still the committed format A spreadsheet is a zip of compressed XML. It does not diff in a pull request, two people editing it cannot merge, and git blame on a scenario stops working. Excel also changes financial data quietly: a code typed as 007 is stored as 7, and a long account number becomes 1.2E+15. So the spreadsheet is where scenarios are written, and YAML is what gets committed and reviewed.

That command loads every row against a schema and fails on a typo, an unknown tag or a persona that does not exist — before any test runs. A test that silently matched nothing is the failure mode it exists to prevent.

What to take from lesson 04
  • A scenario is a readable file, not code, so domain experts can write tests.
  • The human's expected verdict is stored alongside, which is what lets the graders themselves be scored.
  • The corpus is validated against a closed vocabulary before anything runs.

Lesson 05 · Setting up a test

The customer on the other side

In one sentence Somebody has to play the customer, and how convincingly they play it decides what your test can possibly discover.
The everyday version

Medical schools hire actors to play patients. The actor is briefed: you have this pain, you are frightened, and you will not mention the chest tightness unless the student asks an open question.

That last instruction is the whole point. If the actor volunteers everything, the exam cannot tell a good history-taker from a bad one.

This project

A holds concerns, objections and a manner. Facts it will not volunteer are , released only when properly asked.

Concerns revealed and objections raised are written into the as tool calls, so a grader can count them instead of guessing.

The design decision worth stealing

The persona decides the move. A separate voice decides the words.

So the state machine says "raise the fee objection now", and only then does something turn that into a sentence — a fixed line, or a language model, or synthesised speech. If the voice could change the move, you would have two customers disagreeing with each other and no way to tell which one your result came from.

Three ways the customer can be played

  • Scripted. Fixed lines. Free, instant, perfectly repeatable — and it cannot surprise you.
  • Live. A real language model plays the customer, paraphrasing and pushing back. This is what the grader will actually face in production. Costs money, so runs are recorded and replayed afterwards.
  • Spoken. The live conversation, with every line really synthesised to audio and really transcribed back. This is where channel defects appear that no text test can find.
What to take from lesson 05
  • The simulated customer withholds facts on purpose, so the test can tell good questioning from bad.
  • Deciding the move and wording the move are deliberately separate jobs.
  • Scripted, live and spoken are three depths of the same test.

Lesson 06 · Setting up a test

The adapter: pointing it at your own agent

In one sentence An adapter is a small piece of code with two methods that lets the harness talk to any agent without either side being rewritten.
The everyday version

A travel plug. Your hairdryer is unchanged. The Italian wall socket is unchanged. A cheap adapter sits between them and both carry on being themselves.

What you would not accept is a hotel that requires you to rewire your hairdryer before it can be plugged in.

This project

The harness never asks your agent to inherit from anything or import anything. It asks for an object with two methods: open() and reply(customer_turn).

That is the whole . Return None from either to mean "I am finished".

What it looks like

class MyTrainee:
    def open(self):
        return "Good morning. What brought you in today?"

    def reply(self, customer_turn):
        answer = my_agent.send(customer_turn)   # your system, however it works
        return answer or None                   # None means "I'm done"

Then you tell the harness where to find it, and run:

export LAB_TRAINEE_FACTORY="mypackage.adapters:build"
python -m roleplay.live

That string is a to a function. The harness imports it at run time. Nothing in the harness mentions your code and nothing in your code mentions the harness.

Worked examples in the repository
examples/adapters/echo_trainee.pyThe smallest possible one. Read this first.
examples/adapters/http_trainee.pyAn agent living behind a web request.
examples/adapters/callable_trainee.pyWrapping a plain function.
docs/ADAPTER.mdThe full write-up, including the second seam for voice.
Why this matters more than it looks Most evaluation tools ask you to rewrite your agent into their abstractions before they will measure it. That cost is paid up front, by the team least able to spare it, and it is why so many eval projects are started and abandoned. Two methods and an environment variable is a deliberately low price.
What to take from lesson 06
  • Two methods, open() and reply(), are the entire contract.
  • It is a protocol, so there is no base class and no import in either direction.
  • An environment variable names your factory; everything downstream is unchanged.

Lesson 07 · Judging

Contracts: the six inspectors

In one sentence A contract is a mechanical question asked of the recording, which can only answer pass, fail, or "this did not apply here".
The everyday version

A building inspector's checklist. Is there a smoke alarm on every floor? Is the fire door self-closing? Each is a yes or no that two inspectors would answer identically.

"Is the kitchen tastefully decorated?" is not on the checklist. That is a matter of opinion, and it belongs to a different process.

This project

Six , each reading the . No model is called; the same trace always gives the same answer.

Matters of opinion go to a instead — the next lesson.

The six, and the question each asks
ToolContractWas the right tool called, the right number of times, with the right arguments, in the right order?
PromiseContractThe agent said it had done something. Did it actually do it? This is the said-versus-did check.
NoReAskContractDid the agent ask for something the customer had already given it?
FieldPropagationContractThe customer gave a fact. Did that fact survive into what the agent did next, or was it collected and forgotten?
NoProgressContractDid a turn move the conversation forward at all, or did it just fill air?
PhraseContractWas a required thing said, or a forbidden thing avoided — allowing for paraphrase, not exact strings?

Two details that make them trustworthy

They decide on position, not on time

"Was the disclosure given before the recommendation?" is settled by comparing places in the list of events — event 7 comes before event 11. Not by comparing timestamps. A slow laptop, a retried network call or a busy CI machine can move timestamps around; none of them can reorder the list.

A check that did not apply says so out loud

Three answers, not two: pass, fail, and not applicable. If no objection was ever raised, the objection-handling check does not quietly pass — it reports that it had nothing to look at, and the shrinks visibly.

The failure mode this prevents A check that passes because it never found anything to examine is called a , and it is the most dangerous kind of green: your suite gets quieter and looks healthier at exactly the moment it stops working. The engine counts vacuous passes deliberately. This repository has twice caught a check of its own that could no longer fail anything.
What to take from lesson 07
  • Six contracts, each a mechanical yes-or-no over the trace, with no model involved.
  • Ordering is judged by position in the event list, never by clock time.
  • "Not applicable" is a real third answer, and vacuous passes are counted rather than enjoyed.

Lesson 08 · Judging

Judges, and why you must test the judge first

In one sentence Some questions need taste rather than counting, so an AI marks the work — and here it is not allowed to mark anything until it has passed an exam of its own.
The everyday version

A school hires a new examiner. Before they mark anything real, they are given a stack of papers whose correct grades are already known, and their marking is compared with the answer key.

If they pass every weak paper, they do not get the job — no matter how confident or fluent their comments are.

This project

An AI reads a transcript and answers a question. Before it can decide anything, it is run over hand-labelled examples: .

require_calibrated() raises an exception below the threshold. Not a warning in a log. The build stops.

The two numbers that decide it

The worked example in this repository

One judge was written to detect a specific failure. Measured against hand-labelled examples, version 1 scored:

  • True-positive rate 0.250 — it caught 2 of the 8 real failures.
  • True-negative rate 1.000 — it correctly left all 16 good ones alone.

Judged on overall agreement it looked respectable: 18 of 24 correct, 75%. Judged on the only thing that mattered, it missed three failures out of four. The gate refused it. A rewritten prompt reached 1.000 on both, and only then was it allowed to decide anything.

Two honest caveats the repository prints beside that result Eight items out of eight is a small sample: the statistical interval around it stretches down to 0.68, which is below the very threshold it passed. And when the same study was run three times, the totals were identical while two individual items flipped verdicts in opposite directions and cancelled out. Aggregate agreement is not agreement. Both facts are published next to the number rather than left for someone else to find.

What to take from lesson 08
  • A judge is an AI marking an AI, and is useless until measured against human labels.
  • Two rates matter: how many real failures it catches, and how many good ones it leaves alone.
  • Failing the gate raises an exception, so an uncalibrated judge cannot quietly become load-bearing.

Lesson 09 · Judging

Scoring: points you can trade, gates you cannot

In one sentence Some things are worth points; some things are pass-or-fail whatever your points total — and confusing the two is how compliance failures get averaged away.
The everyday version

The driving test again. Smooth gear changes and good mirror use earn marks. But if you run a red light, you fail — with any number of marks.

Nobody would accept "I ran the red light but my parallel parking was excellent, so on average I passed."

This project

The has 28 items. Nineteen carry points. Eight are worth zero points.

A gate is worth zero on purpose, so the code cannot accidentally include one in a total. There is no filter to forget.

Two mark schemes, and why both are kept

The shipped one, and the cited one
rubric_v1What the product shipped with: five criteria, four points each, pass at 14 of 20. It cites no source and carries three deliberate defects.
the scorecard28 items, each with a named detector, a stated , and a regulatory source or an explicitly labelled assumption.

The old one is kept on purpose, as the specimen. Here is what it does, on two real recorded calls:

  • The shipped rubric scored compliance by counting six English keywords in what the adviser said. Both calls got 4 out of 4.
  • The cited gate read the product's own — the list of disclosures it actually recorded. One call had recorded 2 of 3 required disclosures; the other 1 of 3.
  • Same recordings, same information available. One instrument was reading vocabulary; the other was reading facts.
Why "denominator" appears everywhere in this project A rate without its denominator is treated as a defect here. "20% of calls failed" could be 1 of 5 or 2,000 of 10,000, and those are different claims. So every rate in the code and in every report carries the count behind it. When a check does not apply, the denominator shrinks and the report says so — rather than the item quietly scoring zero or quietly scoring full.

What to take from lesson 09
  • Points are tradeable; gates are not, and gates are worth zero points so they cannot be averaged in.
  • Reading the product's own record beats reading its words.
  • Every rate carries its denominator, and a check that did not apply reduces the denominator visibly.

Lesson 10 · Judging

Running it more than once

In one sentence An AI can pass by luck, so a test that passed once has told you almost nothing.
The everyday version

Somebody parallel parks perfectly on their first attempt. Have they learned to park? Ask them to do it five more times.

If they manage three out of six, the honest answer is not "pass" and not "fail". It is unreliable, and that is its own useful finding.

This project

: run the same scenario k times and require it to pass every time.

A test that passes sometimes gets a third verdict, — never counted as a pass.

Three verdicts, not two: STABLE_PASS, STABLE_FAIL, FLAKY. Making unreliability its own answer is the difference between a suite that measures behaviour and a suite that measures luck.

The harness has its own wobble, and it is measured

If you run the identical thing twice and get different answers, some of that is the agent and some is the rig itself. This project measures the rig's own variability rather than assuming it away, so a small difference can be told apart from a real regression.

The subtle finding hiding in the stability work One prompt returned exactly the same summary numbers on three separate runs — and looked perfectly stable. Item by item, two of twenty-four items flipped their verdicts between runs, in opposite directions, cancelling out. Aggregate stability is not stability. Only the per-item view could see it, which is why the report keeps both.
What to take from lesson 10
  • Run it k times and require every run to pass.
  • FLAKY is a first-class verdict, never rounded up to a pass.
  • The rig's own variability is measured, and totals can hide item-level instability.

Lesson 11 · Voice, and the rest

Voice: the telephone game

In one sentence When an agent speaks and listens, two extra translations happen — and things get lost in them that no typed test can ever see.
The everyday version

The party game where a sentence is whispered around a circle. Nobody lies. Everyone hears slightly wrong, and by the end the sentence has changed.

Now imagine grading the last person's answer without realising the sentence had changed on the way round.

This project

Text goes through , becomes audio, comes back through . Real engines, really called, recorded and committed.

The grader then marks the final text — which is not the text anyone wrote.

The finding, and the twist that nearly buried it

On a real recorded call, the grader gave 0 out of 4 for asking questions. Five of the adviser's eight turns were questions. The detector checked for a question mark; the graded transcript had none.

Now the part worth remembering. Comparing the spoken run with a perfect-channel counterfactual:

  • Asking questions fell from 2 to 0.
  • Objection handling rose from 2 to 4.
  • The total was 12 out of 20 either way. Same verdict. Same disclosure record.

Anyone checking totals, verdicts or the compliance record would have concluded the audio channel changed nothing. Only comparing criterion by criterion found it. Two errors moved in opposite directions and cancelled.

The word error rate trap is quoted as two numbers here, always. Perfect recognition scores about 0.43 against a synthesis reference, because "0.68 per cent" comes back as "zero point six eight percent" — every word technically different, nothing actually wrong. Normalised, the same pair scores 0.056. Publishing only the raw figure would make a working recogniser look broken; publishing only the normalised one would hide real errors. So both are printed, with a file explaining why.
What to take from lesson 11
  • Speech adds two translation steps, and the grader marks whatever comes out the far end.
  • The raw, unpunctuated transcript is graded on purpose; the cost of that decision was a real defect.
  • Compare per criterion, because two opposite errors can cancel into a healthy-looking total.

Lesson 12 · Voice, and the rest

When the AI looks things up

In one sentence If an agent searches documents before answering, two separate things can go wrong, and averaging them into one score hides both.
The everyday version

A researcher is asked a question. They fetch three books from the shelf, then write an answer.

Two different failures: they fetched the wrong books, or they fetched the right books and then wrote something the books do not say. A single "quality score" cannot tell you which happened — and the fixes are completely different.

This project

means retrieval-augmented generation: look things up, then answer.

ragcheck/ scores the fetching and the writing separately, and refuses to combine them into one number.

  • Retrieval quality. Did it find the right documents? Measured with recall, mean reciprocal rank and normalised discounted cumulative gain — standard search measures, each with its denominator.
  • . Is every claim in the answer actually supported by what was retrieved? Scored one claim at a time.
The case that makes the separation necessary A run with perfect retrieval, precision 1.0, and groundedness of 1 of 2 claims. It found exactly the right documents and then said something they do not support. A suite that only measured retrieval would have reported a flawless result on an answer that was half invented.
What to take from lesson 12
  • Finding the right documents and answering truthfully from them are two different failures.
  • They are scored separately and never averaged.
  • The grader that scores groundedness prints its own agreement with human labels beside its verdicts.

Lesson 14 · The repository

Running it yourself

In one sentence Clone it, install it, and every number in the whole project recomputes on your machine with no account and no API key.

This is a deliberate design rule, not a convenience. Every path that costs money is opt-in behind an environment variable; everything else replays from committed recordings.

git clone https://github.com/Pinglesagar/conversation-eval-lab
cd conversation-eval-lab
make install
The four to run first, in this order
make startPrints the headline finding with the evidence behind it. Start here.
make spoken-replayReplays the recorded spoken call and re-grades it. No network, no keys.
make cited-callsGrades both recorded calls against the cited scorecard, printing which items it could not decide and why.
make testThe full suite: 2,351 pass, 4 skip. The four skips are the live-transport tier, behind a flag.
Then, when you want to go deeper
evallab validateEvery scenario against its schema. A typo fails loudly here rather than silently later.
evallab calibrateThe timing gate and the judge gate. Non-zero exit if either fails.
evallab replay <trace>Re-check any committed trace with no agent running.
evallab select --changed-sinceWhich scenarios a code change can reach. Fail-safe: unsure means run it.
make advisory-verdictsThe 18 compliance rows decided from the four cited registers.
make ragcheckRetrieval and groundedness, separately.
make gateEverything that gates, cheapest first, stopping at the first failure.
What "no API key" actually costs Replay is blind to a prompt change. If you edit a prompt, the recorded conversation does not change, so a green replay proves the checks still work — not that the new prompt is good. That is stated as a limitation in the repository rather than glossed over, and it is why the live paths exist behind their flags.
What to take from lesson 14
  • make start, then make spoken-replay, then make cited-calls, then make test.
  • Everything runs offline because the expensive paths were run once and committed.
  • Replay cannot see a prompt change, and the project says so.
